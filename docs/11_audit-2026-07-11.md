### A. 挙動修正レーン（1件ごとに挙動差の明文化と個別承認が必要）

- [x] **A1【最重要】stale `.wait.lock` の回収機構がない** — `src/core.ts:1425-1449`。lock に pid/at を書くが**読むコードが存在しない**。agent_done 待機中の SIGKILL/OS 再起動で lock が残ると、同 session への `wait:"agent_done"` が EEXIST で無期限拒否。正規回復が session 破壊（pty_close/killAll）か手動削除のみ。待機窓は既定 600 秒×日常操作＝発火現実性高。Codex レビューと Workflow Critic が**独立に同着**。
  修正: EEXIST 時に lock を読み `process.kill(pid, 0)` で liveness 判定 → ESRCH なら unlink して O_EXCL retry（pid 再利用誤判定は拒否側に倒れ fail-safe）。最低限でもエラーメッセージに lock 内 pid/at を出す。
  実在証拠: state root に `pty_list` に居ない孤児 managed home（novel-a-fixtures-*）が現存＝クラッシュ残骸は実際に起きている。
- [x] **A2 close/killAll がプロセス間 wait lock を見ない** — `src/core.ts:935-950, 952-998`。ガードは in-memory `agentWaitLocks` のみ（既存回帰は in-process 検証＝反論不成立）。別プロセスの close/killAll で、待機側は **600 秒ブロック後に空出力＋`agent_timeout`（無診断）**。
  **A1 とセットでのみ修正**（順序: A1 stale 検出 → A2 は「生きている pid の lock のみ拒否」）。A2 単独実装は stale lock が close を塞ぐ改悪。
- [x] **A3 rtk classify の pytest 誤分類が全文を虚偽に置換** — `src/rtk.ts:403`（`command.includes("pytest")` の全文部分一致）＋ `reducePytest`（rtk.ts:62-188）は **null を返せず**、非 pytest 出力が「Pytest: No tests collected」1行に置換される（rtk.ts:369 の C4「誤分類は安全」コメントは pytest reducer に関して偽）。`python run_not_pytest.py` 等で実測再現。オプトイン経路・raw 回収可能だが、能動的に有害な失敗モード。
  修正: classify を絞るのでなく **reducePytest に「pytest 証拠ゼロなら null」ガード**（summary 行パース成功／`FAILURES`・`short test summary` 見出し／`no tests ran in` のいずれか必須）。**罠**: golden fixture 全6件は quiet 形式で "test session starts" ヘッダを含まない＝ヘッダ必須ガードは fixture を壊す。
- [x] **A4 `pty_read` の削減に行長・総量キャップがない** — `src/core.ts:461-478, 919-922`。head+tail 折りたたみは「行数>60」でのみ発火し、**巨大な少数行**（TUI の絶対座標再描画ストリーム等）はそのまま通る。実測: Grok TUI ログ full 読みで 73,176 文字/4行が返り MCP token 上限エラー。MAX_FULL_BYTES(8MB) はメモリ保護でありトークン保護ではない。
  修正: `reduceOutput` の行数 elide 直後に文字量ガード1段（超過行に行内 head+tail＋復元ヒント。行構造は保持＝`line_range` の行番号ドメインを変えない）。screen/full/default が通る単一の絞り口で全非 raw 経路を守れる。
- [x] **A5 `rm -rf -- /` が破壊ゲートを素通り** — `src/core.ts:77`。POSIX の `--` 終端子で対象パターン不一致（実測: `rm -rf -- /` false / `rm -rf /` true）。対象直前に `(?:--\s+)?` 挿入の1行修正。
- [x] **A6 DESTRUCTIVE ゲートが rtk rewrite 後を検査しない** — `src/core.ts:729-773`。検査(732-742)→ `rtkRewrite`(756) で外部バイナリ stdout に置換→未検査で送信。opt-in・信頼バイナリ前提で実害確率低だが、防御の被覆漏れ。rtk 適用後に再検査。
- [x] **A7 line_range "5:3"（下端>上端）が無言で空を返す** — `src/index.ts:147-149`＋`core.ts:881`。負値/NaN は救済済みなのに逆転のみ未処理。raw:true では説明ゼロ（既定経路は 0行メタで空自体は見える）。「フォールバック禁止」原則違反の型＝明示エラー3行＋テスト1件。
- [x] **A8 full/range の 8MB 切り詰めが UTF-8 先頭境界を破る** — `src/core.ts:876`。増分経路の `utf8SafeEnd` と非対称。実害は先頭最大1文字の U+FFFD（cosmetic）だが対称化は S。**副産物**: agent 経路 `core.ts:2026/2078` の `writeOffset(name, safeStatSize(...))` が「off は safeEnd 済み」不変条件(892)を破り得る nit も同時に直す。

### 残余検証点（2026-07-11 実測で解決）

- [x] **信頼できない cwd での project-local hook**（実測結論・安全側で bounded）: `--dangerously-bypass-hook-trust` は **hook trust review** をバイパスするが **directory trust は別ゲートで残る**。マーカー付き project-local `.codex/hooks.json` を仕込んだ未信頼 cwd で `codex_agent(agent_done)` を起動する実験:
  1. 対話 TUI は「Do you trust the contents of this directory? …allows project-local config, **hooks**, and exec policies to load」で停止。**aiterm の ready-gate は自動承認せず** `initial_prompt=not_sent` / session 保全で安全側に止まる（自動発火なし）。
  2. trust を人手で承認した後は project-local hook が**発火する**（managed home の Stop hook と併走。ただし agent_done の turn_done 帰属は壊れない＝完了検出は無傷）。
  - 運用結論: 未信頼 cwd の project hook が黙って走ることはない（trust プロンプトが関門）。ただし trust 承認後は cwd 側 hook が動く＝**信頼しない cwd を承認しないのが利用側の責務**。この関門と発火挙動を [[codex-dangerously-bypass-hook-trust-vs-directory-trust]] として caveat 登録。
